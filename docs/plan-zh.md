# 中文需求与技术方案

## 1. 目标

用户上传最长 30 分钟的英文 PCM WAV 音频。系统把音频切片并行转写，按顺序合并英文文本，再整体翻译为简体中文。系统不是实时工具，不做用户账号、格式转换和说话人识别。

## 2. 用户流程

1. 用户上传音频，获得任务编号。
2. 页面显示 `排队 → 转写 → 翻译 → 完成`。
3. 转写片段可以乱序完成，但最终文本必须按原顺序排列。
4. 单个片段重试后仍失败时，结果保留其他内容，并用时间范围标出缺口。
5. 翻译失败时仍显示英文转写，用户可以再次请求翻译。

## 3. 服务分工

| 服务 | 负责人 | 开发内容 | 答辩重点 |
|---|---|---|---|
| Job | Cao, Mingshu | 上传、任务状态、结果查询、片段排序、去重、合并 | 谁拥有状态；为什么使用 inbox/outbox |
| Audio | Liu, Yingqi | 时长检查、切片、重叠、共享音频文件管理 | 为什么消息只传地址；如何限制压力 |
| Transcription | Yokoi, Yuki | 并行 worker、Whisper 接口、重试、幂等 | worker 崩溃后的消息重投和避免重复 |
| Translation | Zhang, Zhexi | 英译中、超时、重试、熔断器、降级 | 模型不可用时怎样保留可用结果 |

代码量不一定完全相同，但每人都有业务功能、数据库、消息、容错、监控和可说明的设计决定。

## 4. 数据与一致性

- Job Service 是任务状态的唯一负责人。
- 每个片段以 `job_id + segment_number` 标识，重复消息不会产生重复结果。
- 上传和发布 `job.uploaded` 使用数据库 outbox，避免“数据库成功但消息丢失”。
- Job Service 使用 inbox event ID 忽略重复事件。
- 单个服务内部写数据库采用强一致事务；跨服务允许短暂延迟，即最终一致。

## 5. 失败规则

- 普通错误最多重试两次，间隔为 1 秒、2 秒；之后进入死信队列。
- 转写片段最终失败：记录清楚的时间缺口，继续翻译其余内容，任务为 `PARTLY_DONE`。
- 所有片段都失败或切片失败：任务为 `FAILED`。
- 翻译最终失败：英文转写仍可下载，任务为 `PARTLY_DONE`，可人工重试。
- 同时处理中的任务达到 20 个：新上传返回 429，提示稍后重试。

## 6. AI 要求

- 保存 Whisper、翻译模型和 prompt 的版本。
- 相同模型版本的第一次结果保存后不自动覆盖，以处理非确定性。
- 监控每段处理时间、每分钟音频所需时间、翻译 token 数。
- 默认模拟 AI 费用为 0；最终测试可换成本地 Whisper 和 Ollama。
- Ollama prompt 把转写内容标记为不可信数据，不给模型任何工具权限。

## 7. 最小验收测试

1. 上传 65 秒文件，应生成 3 段，乱序结果仍正确合并。
2. 重复发送同一片段消息，数据库只有一条结果。
3. 转写中杀掉 worker，重启后任务继续且无重复。
4. 注入第 2 段失败，最终状态为 `PARTLY_DONE` 并显示缺口。
5. 注入翻译失败，英文文本仍显示；恢复后重试成功。
6. Dashboard 可看到请求量、错误、延迟、队列、处理时间和 token。
